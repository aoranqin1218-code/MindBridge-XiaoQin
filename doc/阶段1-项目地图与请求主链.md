# 阶段 1｜项目地图与请求主链

> 目标：脱离文档讲出“页面请求 → FastAPI → ChatService → Harness → Runtime → SSE”的职责边界和调用顺序。当前状态：已完成；真实 SSE 帧抓取作为可补充运行证据后置。

## 本阶段主链

```text
页面 POST /api/chat/stream
  → FastAPI Route：认证、角色限制、数据库依赖、返回 StreamingResponse
  → ChatService.stream_chat：组织 SSE 生命周期
  → MindBridgeAgentHarness.run：单轮业务编排、持久化、Trace、工具计划
  → EventDrivenAgentRuntimeService.run：受控事件驱动多 Agent 协作
  → Runtime 返回 response_messages
  → AiClient.stream：按 response_messages 调用模型并产生 token
  → ChatService 发送 meta / token / done SSE 事件
  → token 完整结束后保存助手消息，再投递后置工具任务
```

关键边界：Runtime 不直接向页面推送 token；它返回供模型生成最终回复的 `response_messages`，`ChatService` 再调用 `AiClient.stream(...)` 并编码为 SSE。

## README 建立的项目地图

- 产品定位：校园心理支持后端；普通聊天、咨询和风险输入共享同一入口，但 Runtime 会进行 `CHAT / CONSULT / RISK` 路由。
- Web 边界：FastAPI + Uvicorn/ASGI 接收 HTTP 请求；学生聊天使用单向 SSE 流式响应。
- Runtime：Coordinator、Understanding、Safety、Context、Response 围绕共享黑板、任务 Claim、Artifact、安全审查和最终采纳协作；不是经典 ReAct，也没有模型原生 Function Calling。
- 数据与上下文：MySQL 保存完整业务数据；Redis 保存短期记忆；ContextAgent 按需使用 Chroma + BM25 混合检索和 Skills。
- 后处理：报告形成后生成工具计划。队列开启时写入异步工具任务并由内部工具服务执行；队列关闭时才通过 MCP client 调用 MCP Server。两条路径不能混称。
- 两种 Harness：Agent Runtime Harness 管一轮线上 Agent 业务编排；Engineering Harness 管可重复的工程验证，两者职责不同。
- 项目根目录已新增 `项目目录结构说明.md` 作为长期查阅地图，区分产品源码、内容资源、测试/评测、运行数据和生成产物，并给出各阶段的文件入口。

## 技术选型与边界

### SSE

- 是什么：基于普通 HTTP 长连接，由服务端持续发送文本事件。
- 为什么使用：聊天主要是服务端向浏览器单向推送 token，协议简单，并可继续使用现有 HTTP 认证和路由。
- 替代方案：WebSocket 支持全双工通信，适合双向实时控制；普通 JSON 响应最简单，但必须等待整段回复完成。
- 局限：SSE 主要是单向通道；断线恢复、代理超时、错误事件和取消策略仍需应用自行设计。

### 分层职责

- `app/main.py` 是应用的 composition root（装配根）：它负责把配置、数据库初始化、工具 Worker、路由、中间件和静态资源接入同一个 FastAPI 生命周期；具体业务实现仍归各自模块，不能把初始化逻辑本身堆进 `main.py`。
- Route 拥有 HTTP 协议边界，不拥有 Agent 业务编排。
- ChatService 拥有 SSE 输出顺序，不拥有多 Agent 内部协作。
- Harness 拥有一次 Agent turn 周边的输入准备、持久化、Trace 和工具计划。
- Runtime 拥有多 Agent 任务、Claim、Artifact、安全复核和最终采纳。

## 阶段笔记

### `app/main.py`

**中间件 `no_cache_frontend_assets`**

拦截每个 HTTP 请求，对以 `/` 或 `.html/.js/.css` 结尾的路径在响应头中加上 `Cache-Control: no-store`，告诉浏览器不要缓存。目的是 SPA 前后端一体部署时保证前端静态文件每次都能拿到最新版本，不被浏览器缓存旧版本。

`call_next` 不是导入的，是 Starlette 在调用中间件时自动注入的回调——把请求交给链条上的下一环处理，拿到响应后再由中间件做手脚（如加头）。

**`on_event` → `lifespan` 改造**

`@app.on_event("startup")` / `@app.on_event("shutdown")` 在 FastAPI 0.93+ 已弃用，应改为 `lifespan` 异步上下文管理器。`yield` 之前的代码是启动逻辑（建表、种子数据、启动 worker），`yield` 之后是关闭逻辑（停止 worker）。`FastAPI(lifespan=lifespan)` 传入后，框架会在合适的时机调用它。`lifespan` 定义在 `create_app` 内部作为嵌套函数，外部不可见，唯一用途就是传给 `FastAPI` 构造函数。

`app` 作为参数传入 `lifespan` 的原因：定义函数不等于调用函数，`lifespan` 只是被定义了，FastAPI 启动时内部调用 `lifespan(self)`，用真实实例填充参数——本质是回调。

**静态文件挂载**

```python
static_dir = Path(__file__).resolve().parent / "static"
app.mount("/", StaticFiles(directory=static_dir, html=True), name="static")
```

把 `app/static/` 目录挂载到根路径 `/`。路由匹配顺序决定业务逻辑：API 路由（`include_router`）先注册，优先匹配 `/api/*` 等路径；匹配不到的请求落到 `StaticFiles`，从 `static/` 目录找文件返回。`html=True` 让目录请求自动找 `index.html`。一个进程同时提供前端页面和后端 API，无需分开部署。

### `app/core/database.py`

**SQLAlchemy 会话**

`SessionLocal = sessionmaker(bind=engine, ...)` 是会话工厂。调用 `SessionLocal()` 意思是"从连接池借一条数据库连接，返回一个会话对象"，用完 `db.close()` 归还。它不是"创建数据库实例"，而是借连接。

项目中两种"session"需要区分：
- SQLAlchemy `Session` — 数据库连接（路由参数 `db: Session`）
- `ChatSession` ORM 实体 — 一次聊天会话记录（`outcome.session`）

`public_id` 是给前端看的会话 ID（随机字符串），与内部自增 `id` 分开，防止暴露数据量、防止被遍历。

---

### `app/core/security.py`

**Basic Auth**

浏览器在请求头加上 `Authorization: Basic base64(用户名:密码)`，服务端解码验证。Base64 只是编码不是加密，必须搭配 HTTPS 使用。

调用链：`_credentials(request)` 解码请求头提取用户名和密码 → `current_user(request, db)` 查数据库验密码，返回 `UserAccount` → `require_admin(user)` 复用前者再检查角色，不够返回 403。

### `app/api/routes.py`

**`Annotated` + `Depends` 依赖注入**

```python
user: Annotated[UserAccount, Depends(current_user)]
db: Annotated[Session, Depends(get_db)]
```

`Annotated[X, Depends(f)]` 告诉 FastAPI："参数类型是 X，调用 `f()` 获取值"。`get_db` 借数据库连接，请求结束自动 `close()`；`current_user` 从请求头解析认证信息、查库返回用户。路由函数直接用参数，不用自己写连接或认证逻辑。

认证在路由层已保证：进入 `chat_stream` 时 `user` 已通过 `Depends(current_user)` 验证，且第 49-50 行额外拒绝管理员发起对话。

### `app/services/chat.py`

**`stream_chat` 完整流程**

```
harness.run() → yield meta → async for ai.stream() yield token → 存助手消息 → dispatch_tools() → yield done
```

每一段职责：

1. `harness.run()` — 同步跑 Agent 业务编排：脱敏、会话管理、多 Agent 分析（意图/风险/上下文）、拼装 `response_messages`、创建心理报告、生成 `tool_plan`。返回结构化 `AgentHarnessOutcome`。

2. `yield sse("meta", ...)` — 推送会话 ID 给前端，前端记录本次对话。

3. `async for self.ai.stream(outcome.response_messages)` — 逐 token 调 LLM 生成最终回复。`async for` 是因为内部是异步 HTTP 流式请求，等待 I/O 时不阻塞其他请求。每个 token 同时推前端（逐字显示）和存本地列表（`assistant`）。

4. `save_assistant_message` — 流式结束后拼完整文本一次写入数据库。

5. `dispatch_tools(tool_plan)` — 异步执行后置工具任务（报告入队/MCP 调用）。`try/except` 只记日志不抛异常，工具失败不影响用户对话体验。异常日志含 `session.public_id` + `report_id` + `exc`，分别用于定位问题和修复操作。

6. `yield sse("done", ...)` — 发结束信号，前端关闭 EventSource 连接。

**SSE 事件类型**（`ChatStreamEvent.type`）：`meta`（会话就绪）、`token`（携带回复片段）、`done`（流结束）。

**`model_dump()`** — Pydantic 方法，把模型对象转为普通 dict，才能被 `json.dumps` 序列化后发给前端。

### 调用时序问题

**为什么 Harness 先运行、AiClient 后流式？**

数据依赖 + 职责分离。`ai.stream()` 需要的 `outcome.response_messages`（完整的系统提示词 + 上下文 + 用户消息）是 `harness.run()` 的产物，Harness 没跑完就没输入给 LLM。职责上，Harness 管业务编排（建会话、脱敏、评估），AiClient 只管纯 LLM 通信——不能把业务和通信混在一个模块里。

**为什么流式后才存消息和投递工具？**

存消息需要完整文本，流式没跑完没有完整文本。工具投递放在这纯粹是"能放这"——只依赖 `outcome.tool_plan`，不依赖流式结果。更重要的是优先保障用户体验：让用户最快看到流式回复，后台工具（可能数秒）放后面，失败也不影响对话。

**`tool_plan` 是怎么来的？**

来自 `harness.run()` 中后台 Agent 的分析结果：`agent_run.assessment`（意图分类、情绪、风险等级）→ `_create_report()` 写入 DB → `AgentToolPlan(report_id, risk_level)`。与 `ai.stream()` 生成的用户可见回复是两条独立链路。后台分析做决策、存报告，前台流式生成用户能看到的文本——互不干扰。

**生成器（Generator）概念**

生成器不是一次性返回全部结果，而是 `yield` 一次吐一个值后暂停，等下次 `next()` 或 `async for` 来再继续跑。类比水龙头——拧一下出一滴，不拧不流。`StreamingResponse` 在内部 `async for` 消费生成器，每拿到一块就写 HTTP 响应流发给浏览器，实现逐字显示效果。

**SSE（Server-Sent Events， 服务器推送事件）**

基于普通 HTTP 长连接，服务端持续发送文本事件。格式为 `event: <事件名>\ndata: <JSON>\n\n`。前端用 `EventSource` 接收，按事件类型执行不同回调。适合聊天场景（单向推送 token），协议简单、沿用现有 HTTP 认证和路由。`media_type="text/event-stream"` 告诉浏览器这是一条 SSE 连接，与 `application/json`（普通 JSON）、`application/octet-stream`（二进制下载）等 MIME 类型区分。

### Python 基础语法拾遗

**`@dataclass`** — 自动生成 `__init__`/`__repr__`/`__eq__` 等样板方法，适合"主要存数据、没复杂逻辑"的类（`AgentToolPlan`、`AgentHarnessOutcome`、`AgentRunResult`）。

**`@property`** — 把方法变成像属性一样访问，不用加括号。适合"不是存出来的，而是算出来的"值，如 `requires_tools` 取决于 `report_id is not None`。

**`*` 拆解运算符** — `*steps` 把列表拆成独立元素，`[*steps]` 解包再装回去 = 浅拷贝。避免往原数据里追加协作事件。

**原始字符串 `r"..."`** — 正则里反斜杠多（`\d`、`\w`、`\b`），不用 `r` 的话 Python 会先转义一次，`\b` 会变成退格符。正则一律写 `r"..."` 是个固定写法。

### `app/core/enums.py`

**`MessageRole(str, Enum)`** — 多继承 `str` 和 `Enum`。`Enum` 让值被锁定（只能取 `USER`/`ASSISTANT`/`SYSTEM`），`str` 让枚举值可直接当字符串用（`==` 比较、`json.dumps` 序列化都不需 `.value`）。Java 没有类的多继承，只支持接口多实现。

`Enum` 通过 `EnumMeta` 元类自动维护双向字典（名字↔值），所以 `MessageRole("USER")` 等价于 `MessageRole.USER`——不是构造函数调用，而是按值查找成员。

### `app/agents/harness.py`

**`harness.run()` 六块编排**

```
① 输入准备：strip → sanitize → _resolve_session
② Agent 运行时：create_agent_runtime().run() → AgentRunResult
③ 存用户消息：save_message(user, session, USER, original_input)
④ 心理报告：_create_report → PsychologicalReport 入库
⑤ Trace 记录：AgentTraceService.save_run(...)
⑥ 汇总返回：AgentToolPlan + AgentHarnessOutcome
```

每块的依赖关系：① 产出了 `session` 和两个版本的输入（脱敏/原始）；② 依赖 ① 的产出；③ 可以放 ② 之前或之后（当前放之后是因为 `session` 已 commit）；④ 依赖 ② 的 `agent_run.assessment`；⑤ 依赖 ② 的全部结果；⑥ 汇总前面所有产物。

**`agent_run` 的两个关键输出**

- `requires_report`（`@property`）：`intent != CHAT` → 闲聊场景跳过后置工具
- `assessment`（`PsychologyAssessment | None`）：emotion（情绪标签）、emotion_score（0~4）、risk（LOW/MEDIUM/HIGH）、confidence（0~1）、summary（评估摘要）

**`save_message` — MySQL + Redis 双写**

```python
self.db.add(ChatMessage(...))      # 插入 chat_messages 表
session.touch()                    # 更新会话 updated_at
self.db.add(session)               # 标记会话变更
self.db.commit()                   # 一个事务提交 INSERT + UPDATE
self.memory.append(...)            # 同步写 Redis 短期记忆
```

`session.touch()` 只是 `self.updated_at = now()`——每次有新消息，对应会话的时间戳同步刷新。`commit()` 不是逐条提交，而是把当前事务里所有待处理变更一次性刷到数据库。

**`_resolve_session` — 会话查找/新建**

前端带 `public_id` → `query(ChatSession).filter(...).first()` 查已有记录。前端没传（首次对话）→ `ChatSession(public_id=uuid.uuid4().hex, ...)` 创建内存对象 → `add` 标记 → `commit` 写入 → `refresh` 拉回 DB 生成的 id 和时间戳。`refresh()` 是必须的——因为自增 `id` 和 `created_at`/`updated_at` 只有数据库知道，commit 后对象还是旧值。

**`ChatSession(...)` 创建 ORM 对象 ≠ 写入数据库**

`ChatSession(public_id=..., user_id=..., title=...)` 只是在 Python 内存里创建了一个对象，数据库里还没有。必须 `self.db.add(...)` + `self.db.commit()` 才能变成数据库里的一行。这是 ORM 的核心概念——Python 对象和数据库记录是两回事。

**`dispatch_tools` — 两种执行路径**

```python
if report_id is None → 无事可做，return []
工具队列开启 → ToolQueueService.enqueue_report() → 写 tool_jobs 表 → Worker 异步执行
工具队列关闭 → MindBridgeMcpToolClient.handle_report() → 直接调 MCP Server 同步执行
```

- **工具队列**：异步解耦、持久化、可重试、需 Worker 进程（生产环境）
- **MCP**：同步直接、零配置、无持久化（开发/调试）

MCP 不是备选方案——它是**协议层**（统一工具发现和调用格式），工具队列是**执行层**（调度/重试/限流），理想架构里两者叠加使用。

**`sessionId` 前后端流转**

```
首次：前端 state.sessionId = null → POST 请求体 { sessionId: null }
    → 后端 _resolve_session 新建 ChatSession(public_id=uuid.uuid4().hex)
    → SSE meta 事件返回 { "sessionId": "cs_a3f7b2..." }
    → 前端收到 meta → state.sessionId = "cs_a3f7b2..."
后续：POST 请求体 { sessionId: "cs_a3f7b2..." }
    → 后端 _resolve_session 查到已有会话 → 继续同一对话
```

### `app/models/entities.py`

**`Mapped[T]` + `mapped_column()` vs `relationship()`**

| | `mapped_column` | `relationship` |
|---|---|---|
| 数据库有列 | 有 | **无**，纯内存对象引用 |
| 作用 | 存数据（定义列类型、约束） | 关联对象，方便导航 |
| 例子 | `id`、`title`、`user_id` | `session.user`、`session.messages` |

`Mapped[int]` 管 Python 类型注解，`mapped_column(Integer, primary_key=True)` 管数据库列属性——两者配合才算完整 ORM 字段。

**`ChatSession` 与 `ChatMessage` 的一对多关系**

`ChatSession` 是容器（一次完整对话），`ChatMessage` 是内容（一条具体消息）。`session_id` 外键把多条消息关联到同一个会话。`relationship(cascade="all, delete-orphan")` 保证删除会话时自动级联删除其下所有消息。

### `app/services/privacy.py`

**`PrivacySanitizer` — 正则脱敏**

把用户输入中的敏感个人信息用 `[已脱敏]` 替换后传给 LLM，避免泄露到外部 API（OpenAI 等）。

三个正则模式：`1[3-9]\d{9}`（手机号）、`[\w.+-]+@[\w-]+(?:\.[\w-]+)+`（邮箱）、`\b\d{17}[\dXx]\b`（身份证号）。`\b`（单词边界）、`\d`（数字）、`\w`（单词字符 = `[a-zA-Z0-9_]`）。`re.compile()` 把正则字符串编译为可重复使用的模式对象。

### `app/services/trace.py`

**`AgentTraceService.save_run()` — Trace 持久化**

将 Agent 运行完整上下文写入 `agent_run_traces` 表。简单值（`intent`、`risk_level`、`original_input`）直接存列，复杂结构（步骤列表、知识片段、消息列表、评估结果）序列化为 JSON 存 TEXT 列——trace 是运行快照，写入后只做回溯查看，不必建关联表做 join 查询。

**`_to_jsonable()` — 递归序列化**

```python
Enum → .value（RiskLevel.HIGH → "HIGH"）
@dataclass → asdict 后递归处理
Pydantic → model_dump 后递归处理
list/tuple → 逐元素递归
dict → key 转 str，value 递归
原生类型 → 直接返回
```

每层都递归调用自己，保证多层嵌套（dataclass 里套枚举里套 dict）也能剥干净。

**`_json()` — JSON 序列化封装**

`json.dumps(..., ensure_ascii=False)` 让中文不被转成 `\uXXXX`；`default=str` 作为兜底，遇到无法序列化的对象时转成字符串而不抛异常。

**`_agent_steps_with_collaboration()` — 统一时间线**

把 Agent 步骤（`AgentStep`）与协作事件（`collaboration_events`）、协作任务（`collaboration_tasks`）、协作产物（`collaboration_artifacts`）拼成同一个列表，用 `kind` 字段标记类型。三种对象来源不同、结构不同，但合并后能按时间线还原"这一轮 Agent 内部都发生了什么"。

### `app/services/tool_queue.py`

**`enqueue_report()` — 按风险等级触发任务**

| 条件 | 任务 | 作用 |
|---|---|---|
| 只要有报告 | `EXCEL_REPORT` | 生成 Excel 心理评估报表 |
| MEDIUM 或 HIGH | + `CASE_CREATE` | 创建干预个案 |
| HIGH | + `ALERT_SEND` | 发送高危预警通知 |

**可靠性机制**

- **幂等**：`_find_or_create` — 同 report + 同 kind + 状态为 PENDING/RUNNING/SUCCESS 时不重复创建
- **限流**：`RateLimiter` — 邮件预警每分钟有上限，超出后 `_requeue` 延时重试
- **重试**：`attempts < max_attempts` 时指数退避（`retry_delay * max(1, attempts)`），自动重试
- **死信**：`attempts >= max_attempts` 时标记为 DEAD 并写入 `DeadLetterRecord` 表，供人工处理
