# 阶段 0｜启动项目与真实依赖验收

> 目标：先能区分“页面能打开”“Mock 演示通过”和“真实依赖已接通”，再进入后端源码主链。当前状态：**已完成**。Mock + SQLite、Docker MySQL/Redis/Chroma、百炼聊天/向量模型、普通咨询与高风险闭环，以及 Redis 缺失时 MySQL 回填均已验收；下一步进入阶段 1 的源码主链。

## 这阶段真正要建立的认知

### 1. 应用启动不等于所有能力已验证

学生端页面能打开，只能证明 FastAPI 服务和静态资源可用；它不能证明数据库、Redis、模型或向量检索已经真正工作。MindBridge 的完整链路还需要：

`FastAPI → Agent Runtime → MySQL/Redis → 模型 → RAG → 工具后处理`。

所以本阶段把验证拆成三层：

- **Mock + SQLite**：验证确定性的业务闭环和前后端观察效果。
- **真实 MySQL / Redis / 模型**：验证状态、记忆和模型调用。
- **Chroma + Embedding**：验证真正的向量 RAG；BM25 降级不能当作 Chroma 成功。

### 2. Uvicorn、ASGI 与虚拟环境

- **ASGI** 是 Python Web 应用与服务器之间的异步接口约定；它让 FastAPI 能处理异步请求和 SSE 流式响应。
- **Uvicorn** 是实现该约定的服务器，负责监听端口并把 HTTP 请求交给 `app.main:app` 这个 FastAPI 应用对象。
- `.venv` 是项目隔离的 Python 解释器和依赖目录；`Activate.ps1` 的作用是让当前 PowerShell 优先使用它，不会安装依赖，也不会永久修改系统 Python。

### 3. SQLite、MySQL 与 Redis 的分工

- **SQLite** 是一个数据库文件，零服务配置，适合演示、测试和缩小排错范围。
- **MySQL** 是独立数据库服务，适合真实多用户的持久化、账号权限和并发访问；MindBridge 用它保存会话、消息、报告、Trace 和工具任务。
- **Redis** 是内存型键值数据库，MindBridge 用它保存短期上下文；缺失时再由 MySQL 回填。它不是“Python 的 redis 包”，后者只是客户端。

### 4. Docker 与 Docker Compose

- **Docker** 将应用及依赖放入隔离的 Linux 容器，降低 Windows 本机环境差异对复现的影响。
- **Docker Compose** 用一份 `docker-compose.yml` 同时定义并启动 `app`、`mysql`、`redis`，让它们拥有固定版本、服务名和数据卷。
- 容器内的应用通过 `mysql`、`redis` 访问中间件；宿主机通过映射端口观察它们。容器删除不必然删除数据，数据卷才是持久化边界。
- Docker 让项目回到作者的 Linux + Python 3.12 基线，能避开 Windows + Python 3.12 安装旧版 Chroma 原生扩展时的本地 C++ 编译问题；但它不能自动解决模型配置或旧依赖的运行时兼容问题。
- Compose 用 `${变量名}` 注入配置时，当前 PowerShell 的同名环境变量优先于项目 `.env`。因此修改 `.env` 后若容器仍拿到旧配置，应在同一终端先清除旧变量，再强制重建目标容器；这是“配置来源优先级”问题，不是 Docker 未重建。

### 5. Chat 模型、Embedding 与 OpenAI 兼容协议

- 聊天模型负责理解、风险判断和生成回复；**Embedding 模型**负责把文本转换成向量，用于语义检索。二者不能互相替代。
- 当前选用百炼的 `qwen3.7-flash-2026-07-15` 作为聊天模型、`qwen3.7-text-embedding` 作为向量模型。快照模型的版本固定，更适合复现、评测和回归。
- `AI_PROVIDER=openai` 表示项目使用 OpenAI 兼容的 HTTP 协议，并不代表供应商必须是 OpenAI。百炼兼容该协议，故无需重写聊天和向量调用代码。
- 当前项目聊天调用 `/chat/completions`，向量调用 `/embeddings`。`OLLAMA_EMBEDDING_MODEL` 尚未被向量存储代码实际使用，因此不能仅配置 Ollama 就声称向量 RAG 已本地化。
- `OPENAI_BASE_URL` 必须是完整 URL，包含 `https://`（或 `http://`）协议前缀；只有域名和路径时，HTTP 客户端不知道该使用哪种传输协议，会在调用聊天或 Embedding 前直接拒绝请求。
- 对百炼的 OpenAI 兼容接口，Base URL 还必须以 `/compatible-mode/v1` 结尾；MindBridge 再追加 `/chat/completions` 或 `/embeddings`。只填服务根域名会得到 404，而不是模型或 Key 错误。
- 百炼工作区专属域名只接受同一工作区的 API Key；路径正确后若返回 401，优先检查 Key 是否属于该工作区。北京公共兼容域名不绑定单一工作区，适合本项目快速联调，但专属域名更利于工作区隔离。

### 6. Chroma 与 BM25 的边界

- **Chroma** 存储向量并做语义近邻检索；**BM25** 按关键词相关度检索。项目融合两者，并在向量服务异常时可回退到 BM25。
- `KNOWLEDGE_VECTOR_REQUIRED=true` 的意义是：本轮集成必须暴露 Chroma 或 Embedding 的错误，不能静默降级后误判“RAG 已完成”。
- 当前项目是受控事件驱动多 Agent Runtime，不是 ReAct 自主循环，也没有模型原生 Function Calling；MCP 与异步工具队列也不是同一条执行路径。
- OpenAI 兼容的流式响应不保证每一帧都有文本；百炼结尾的用量帧可能 `choices=[]`。解析器应跳过空 `choices` 帧，等待协议结束后再由业务层发送 SSE `done`，不能直接访问 `choices[0]`。

### 7. “满血运行”的验收边界

- 已证实的核心链路：真实 Qwen 聊天与 Embedding、Chroma 查询、MySQL 报告/案例/Trace 持久化、Redis 多 Agent 短期记忆、7 个 Skill 注入，以及高风险后的 Excel 留档、案例创建、告警任务队列。
- 这不是纯前端或 Mock 演示：高风险报告、`ALERT_SENT` 案例、成功的工具任务和包含 Agent 步骤/RAG 结果的 Run Trace 都存在于 Docker MySQL。
- 当前不是外部生产告警：`ALERT_EMAIL_DELIVERY_MODE=log` 只记录告警，不真实发送邮件；这是联调安全配置。
- `ToolGovernanceService` 的策略与审计表已实现，但当前异步队列路径尚未调用它，故不能声称“工具执行已完成策略审计”；这是后续可改进项。

## 当前应能回答的面试问题

1. **为什么已有本机 MySQL/Redis 还用 Docker？** 为了固定版本、网络和数据卷，减少换机器后的环境漂移；代价是要管理镜像、容器和端口映射。
2. **为什么聊天和 Embedding 分开选模型？** 一个生成与推理，一个做向量表示，优化目标完全不同。
3. **为什么 Qwen 能走 `AI_PROVIDER=openai`？** provider 名称描述协议适配器；百炼提供 OpenAI 兼容接口。
4. **为什么不能把 BM25 回退结果说成 Chroma RAG？** 它证明关键词检索仍能工作，不证明向量生成、写入和近邻查询都成功。
5. **为什么阶段 0 要先 Mock 再真实依赖？** 先用确定性环境验证业务闭环，再逐个加入外部变量，能更快定位故障。

## 阶段验收结果与后续观察项

- **Redis → MySQL 降级已验证**：在同一个学生会话中先发起对话、再停止 Redis 并追问，应用日志出现 `Redis memory disabled`，随后 `/api/chat/stream` 仍返回 `200 OK`。这证明 Redis 不可用不会中断聊天；`ContextAgent` 会从 MySQL 的 `chat_messages` 回填历史。学生端的 `sessionId` 只存在当前页面内存，故测试中不能关闭、刷新或点击“重新开始”。
- **后续源码学习观察项**：回到 `ToolGovernanceService` 与 `ToolQueueService` 的接线关系，决定是否补齐工具授权审计；同时复查此前发现的黑板任务 Claim/关闭状态不一致问题是否仍存在。

## 每次电脑重启后的运行清单

1. 打开 Docker Desktop，等左下角显示 `Engine running`；无需先启动本机 MySQL、Redis，也无需激活 `.venv`（Docker 运行不使用它）。
2. 在 PowerShell / VS Code 终端进入项目根目录：

```powershell
cd 'F:\Agent开发\MindBridge\Project\mindbridge-py'
docker compose up -d
docker compose ps
docker compose logs --tail=50 app
```

3. 验收标准：`mysql`、`redis` 为 `healthy`，`app` 为 `Up`；日志含 `Application startup complete.`。首次启动或 Dockerfile / `requirements.txt` 改动后，把第二行替换为 `docker compose up -d --build`。
4. 浏览器打开 `http://127.0.0.1:8080/student.html`；Docker 模式下模型、MySQL、Redis、Chroma 都由当前 Compose 配置决定。
5. 看数据时，DBeaver 连接 Docker MySQL：`127.0.0.1:13306`、库 `mindbridge`、用户 `mindbridge`、密码 `mindbridge`；不要误连本机的 `3306`。
6. 修改 `.env` 后，用 `docker compose up -d --force-recreate app` 让 app 重新读取配置；若当前终端以前设置过 `$env:OPENAI_API_KEY`，先执行 `Remove-Item Env:OPENAI_API_KEY`，避免旧值覆盖 `.env`。

日常停止用 `docker compose down`，它保留数据卷；不要执行 `docker compose down -v`，否则 Docker MySQL 和 Redis 的数据会被删除。

## Docker 常用终端命令

所有命令都先在项目根目录 `F:\Agent开发\MindBridge\Project\mindbridge-py` 执行。

```powershell
# 首次启动或修改 Dockerfile / 依赖后：构建并后台启动 app、MySQL、Redis
docker compose up -d --build

# 查看三个容器是否正常运行
docker compose ps

# 查看应用日志；启动失败或接口异常时优先看这里
docker compose logs --tail=120 app

# 修改 .env 后只重建 app；MySQL、Redis 数据卷不受影响
docker compose up -d --force-recreate app

# 首次镜像下载中断时，先单独拉取，再重新启动
docker compose pull
docker compose up -d --build

# 停止容器，但保留 MySQL / Redis 的 Docker 数据卷
docker compose down
```

不要随意执行 `docker compose down -v`：`-v` 会删除本项目 Docker 数据卷中的 MySQL 和 Redis 数据。
